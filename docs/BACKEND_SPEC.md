# Biman GSE Digital Logbook — Backend Specification

> Implementation specification for the NestJS backend that will replace the mock data in
> `lib/mock-data.ts` / `lib/types.ts`. The PlantUML file `docs/backend-erd.puml` is an approximate
> starting point, not a canonical schema: the backend implementation may improve or restructure
> the entities and relationships when needed. This document describes **modules, workflows,
> business rules, and technical architecture** so an AI agent (or engineer) can implement the
> backend without access to the frontend author's intent.

## 1. Purpose & Domain Summary

NGGL maintains Biman Bangladesh Airlines' Ground Support Equipment (GSE) — belt loaders,
push-back tractors, GPUs, passenger steps, air-start units, etc. This system is a **digital
logbook + CMMS (Computerized Maintenance Management System)**:

- Tracks equipment (assets), their specifications, documents, photos and running hour meter.
- Defines **equipment types**, each with a catalog of **services** triggered by hour-meter bands
  (e.g. Service F: 0–500h, Service B: 500–1000h, ...) or by a fixed calendar interval
  (Service V: every 6 months).
- Raises **maintenance tickets** (work orders). PM tickets use Service F, B, C, D, E, V, or Others:
  - F/B/C/D/E tickets are generated when an authorized user manually triggers an hour-meter service
    check and the equipment crosses the applicable standard service band.
  - `Others` tickets are generated the same way, but for a **custom hour-band service** that an
    equipment type defines in addition to the standard F–E bands (e.g. an extra high-hour service).
    `Others` is therefore not a manually creatable ticket type — it is the auto-generated PM ticket
    type for any custom hour-band service.
  - V-Service tickets are generated by the six-month maintenance schedule.
  - Only Breakdown, General, and Washing tickets are manually created by users.
  - All hour-band services defined on an equipment type — the standard F/B/C/D/E bands plus any
    custom bands — must together form one continuous, non-overlapping range starting at 0 hours,
    with no time/hour gaps between bands (see §5.2).
- Engineers execute tickets: run an inspection checklist, log parts/labour, attach photos, give
  written feedback, and mark functional/safety checks. Completion routes the ticket to
  Manager/Super Admin for verification before closing. Inspection checklist will vary based on service type.
- Engineers may need **parts/equipment requests** fulfilled by Biman Admin during a job.
- All significant actions raise **notifications** to relevant roles.
- Full audit trail of every ticket (`TICKET_HISTORY`) and every hour-meter reading
  (`HOUR_METER_READING`).

## 2. Roles & Organizations

| Role | Organization | Capabilities |
|---|---|---|
| **Super Admin** | NGGL | Full control: user management (create users w/ default password), equipment type CRUD, equipment CRUD, ticket CRUD (create/edit/assign/verify/close), settings, reports, view everything. |
| **Manager** | NGGL | Same operational powers as Super Admin except user management.
| **Engineer** | NGGL | Update hour meter, work tickets assigned to them (start work, fill maintenance record/checklist, submit feedback → triggers verification), create parts/equipment requests, change own password. Read-only on equipment/tickets they are not assigned to (or scoped to "assigned to me" views). |
| **Biman Admin** | Biman Bangladesh Airlines | Create tickets (Breakdown, General, Washing — the "manual" types), describe ticket problems, approve/reject/receive parts requests, view equipment/tickets (read-only), receive/View notifications. Cannot edit equipment, users, or equipment types. |

Notes for backend:
- Users belong to an `organization` (`NGGL` or `Biman`/`Biman Bangladesh`) which is independent of
  `role` but role implies a default org (Biman Admin ⇒ Biman org; other three roles ⇒ NGGL).
- `status`: `Active | Inactive`. Inactive users cannot authenticate.
- Only **Super Admin** creates user accounts, with a **default/temporary password** the new user
  must change on first login (force `must_change_password` flag).
- Any authenticated user can change their own password (old password required).

## 3. Core Modules (NestJS)

Suggested module boundaries (one Nest module per bounded context, each with its own
controller/service/repository, DTOs, and Swagger annotations):

1. **AuthModule** — login (JWT access + refresh token), password change, forced password reset,
   guards (`JwtAuthGuard`, `RolesGuard`), `@Roles()` decorator.
2. **UsersModule** — CRUD for NGGL users (Super Admin only), list Biman users (read-only for
   others), profile/self endpoints.
3. **EquipmentTypesModule** — CRUD for equipment types and their nested `services` (Super
   Admin/Manager), including the contiguous-hour-band validation for F/B/C/D/E and custom
   (`Others`) services described in §5.2.
4. **EquipmentModule** — CRUD for equipment (Super Admin/Manager), specifications, documents,
   photos sub-resources, hour-meter update endpoint (all authenticated roles that touch equipment:
   Engineer/Manager/Super Admin — see §5.3), hour-meter history.
5. **TicketsModule** — ticket CRUD, status transitions, assignment, maintenance record
   (checklist, parts, labour, functional/safety checks), feedback entries, ticket history.
6. **MaintenanceScheduleModule** — V-Service's six-month recurring schedule, due/overdue
   computation, and creation of V-Service tickets when a scheduled occurrence is due. No other
   service type is scheduled.
7. **RequestsModule** (Equipment/Parts Requests) — create, approve, reject, mark received.
8. **NotificationsModule** — persisted in-app notifications, Redis/WebSocket delivery,
   read/unread, and mark-all-read. Email is out of scope for this version.
9. **ReportsModule** — aggregate/analytics endpoints (availability, downtime/MTBF, PM compliance)
   — computed on read initially.
10. **JobsModule** — only background processing that is actually needed, such as V-Service schedule
    checks and notification delivery. Hour-meter service crossing is explicitly triggered by a
    user/API action, not by a scheduler.
11. **StorageModule** — local filesystem storage, image optimization pipeline, file asset metadata,
    safe file serving, orphan cleanup, and storage usage tracking (see §5.11). Other modules never
    access the filesystem directly; they call `StorageService`.
12. **CommonModule** — pagination, filtering, audit interceptor, exception filters, Swagger config.

## 4. Data Model

Use `docs/backend-erd.puml` as an approximate domain sketch only. It is not a canonical ERD and
should not constrain the final Prisma/TypeORM design. The implementation may normalize, split, or
combine entities as appropriate. The following rules are requirements regardless of the final
schema:

- Replace all frontend "display name" fields (`assignedEngineer`, `createdBy`, `actor`,
  `requestedBy`, `approvedBy`, `recordedBy`) with **user ID foreign keys**; join to `User` for
  display name in API responses.
- `Ticket.pmType` / `serviceType` is an enum matching the PM services `F-Service | B-Service |
  C-Service | D-Service | E-Service | V-Service | Others`, or one of `Breakdown | General |
  Washing` for user-created tickets. `Others` is system-generated only (custom hour-band PM
  service) and must never be exposed in the manual-create DTO.
- `MaintenanceRecord` is 1:1 with `Ticket` (created automatically when the ticket is created, from
  the equipment type's checklist template).
- `ChecklistItem` rows are **cloned per maintenance record** from a master checklist template (see
  §5.6) — not shared/mutated globally.
- `WORK_IMAGE` / feedback entries: model engineer feedback as a **collection of timestamped
  entries** (author, html body, image URLs) rather than a single string, since the UI supports
  multiple feedback submissions over the life of a ticket (`FeedbackEntry[]` in
  `app/tickets/[id]/page.tsx`). Add a `TICKET_FEEDBACK` table:
  `id, ticket_id FK, author_user_id FK, body_html, created_at`, with child `FEEDBACK_IMAGE` rows.
- **Files are never stored as raw URLs.** All uploaded binaries are represented by a single
  `FILE_ASSET` table (§5.11), and domain tables reference it by `file_asset_id`:
  `EQUIPMENT_PHOTO(equipment_id, file_asset_id, slot)`, `WORK_IMAGE` / `FEEDBACK_IMAGE`
  (`file_asset_id`), and `EQUIPMENT_DOCUMENT(file_asset_id, name, type, expiry_date)`.
  `EQUIPMENT_PHOTO.slot` is `PRIMARY | FRONT | SIDE | OTHER`, matching the equipment profile UI
  (primary image, front view, side view); `PRIMARY`/`FRONT`/`SIDE` are unique per equipment and
  replacing one deletes the previous asset.
- `EquipmentRequest.ticketId` / `equipmentId` — always tied to a ticket; `equipmentId` is derived
  from the ticket's equipment for convenience/denormalized reporting.
- Store rich text (engineer feedback) as sanitized HTML (sanitize server-side, e.g. with
  `sanitize-html`) — never trust client HTML.
- Add standard audit columns to every table: `created_at`, `updated_at`, and where relevant
  `created_by_user_id` / `updated_by_user_id`.
- Add soft-delete (`deleted_at`) to `Equipment`, `EquipmentType`, and `User` rather than hard
  delete, since tickets/history reference them.

## 5. Business Rules & Workflows

### 5.1 Users & Auth

- Super Admin creates a user with `name, email, role, organization` → system generates a default
  password (or Super Admin sets one), displays it to the Super Admin for secure handoff, and sets
  `must_change_password = true`. Email delivery is not part of this version.
- On first login (or whenever `must_change_password` is true), the user must set a new password
  before accessing any other protected endpoint.
- Users can self-service change password at any time (`PATCH /users/me/password`), requiring
  current password.
- JWT-based auth; `role` and `organization` embedded in the token/claims for guard checks.
- Deactivating a user (`status = Inactive`) invalidates future logins and existing refresh tokens.

### 5.2 Equipment Types & Services

- Super Admin/Manager CRUD equipment types (`EquipmentType`) each holding an ordered set of
  `EquipmentTypeService` records.
- **PM services** are F-Service, B-Service, C-Service, D-Service, E-Service, V-Service, and
  optionally one or more **custom hour-band services** (ticket type `Others`). F/B/C/D/E and any
  custom hour-band services use `minHours`/`maxHours` bands; V-Service uses `months = 6` instead.
- V-Service is the only scheduled service and uses `months = 6`. It is a recurring calendar
  service; F/B/C/D/E and custom hour-band services are never created by a calendar scheduler —
  only by the manual hour-meter service-check (§5.3).
- **Service-band gap validation (required on create/update of an equipment type's services).**
  All hour-band services on an equipment type — F, B, C, D, E, and any custom bands — must
  together form one continuous, non-overlapping sequence of hour ranges starting at 0, with no
  gaps and no overlaps between consecutive bands. V-Service (calendar-based, no hour band) is
  excluded from this check. Validation algorithm:
  1. Collect all hour-band services for the equipment type (`minHours` and `maxHours` set;
     excludes V-Service and any other calendar-only service).
  2. Sort them by `minHours` ascending.
  3. The first band's `minHours` must equal `0`.
  4. For every consecutive pair, `band[i].maxHours` must equal `band[i + 1].minHours` exactly
     (no gap, no overlap). Reject the request with a validation error otherwise, and report which
     two bands have the mismatch (e.g. `"E-Service ends at 3000h but Others starts at 3200h —
     bands must be contiguous"`).
  5. `minHours < maxHours` must hold for every band (reject zero-width or inverted bands).
  6. The last band's `maxHours` may be left open-ended (`null`) to represent "3000h and beyond";
     if present, only the last band (by `minHours`) may have a null `maxHours`.
  7. Custom bands slot into this sequence by their `minHours`/`maxHours` like any other band —
     they are not required to sit after E-Service; validation only cares about continuity, not
     which named service occupies which position.
  8. Re-run this same validation whenever services are added, edited, reordered, or removed, and
     on equipment-type creation.
- A custom hour-band service's ticket type is always `Others`; it does not get its own
  `TicketType` enum value. If an equipment type ever needs more than one custom band, all of them
  share the `Others` ticket type — the specific service is identified via
  `Ticket.pmServiceId` (FK to `EquipmentTypeService`), not by ticket type alone.
- Deleting an equipment type in use by equipment should be blocked or require reassignment
  (default: **block delete if referenced by any equipment**).
- Editing service bands on an equipment type that already has equipment assigned must re-run the
  gap validation and should warn if it changes the currently-active band for existing equipment
  (see §5.3 idempotency — a service reconfiguration should not silently create duplicate or
  missing PM tickets for equipment already in a cycle).

### 5.3 Equipment & Hour Meter

- Super Admin/Manager: full CRUD on equipment (asset no auto-generated as `BGM-###`, sequential),
  specifications, documents, and photos.
- **Hour meter updates**: Engineer, Manager, or Super Admin can update an equipment's hour meter
  (`POST /equipment/:id/hour-meter`). Rules:
  1. New value must be `>= current hourMeter` (monotonic; reject decreases unless a separate,
     explicitly audited correction workflow is implemented).
  2. Persist a new `HOUR_METER_READING` row (value, recordedAt, recordedByUserId); never mutate
     history, only append.
  3. Update `Equipment.hourMeter` to the new value in the same transaction.
  4. **Service crossing is a manual business action.** Updating the meter alone must not create a
     ticket. Provide an explicit action such as `POST /equipment/:id/hour-meter/service-check`
     (or an equivalent button in the frontend) to evaluate the new meter against the equipment
     type's hour-band services — F/B/C/D/E and any custom hour-band services — which are
     validated to be contiguous and gap-free per §5.2.
  5. The manual service-check compares the previous serviced threshold/cycle with the current
     meter. If a new hour band has been crossed:
     a. Create one PM ticket with `serviceType` equal to the applicable standard service
        (`F-Service`…`E-Service`) or `Others` if the crossed band is a custom hour-band service.
        Set `pmServiceId` to the specific `EquipmentTypeService` that was crossed, `priority =
        Medium` by default, `status = Open`, and the authenticated user as actor.
     b. Clone the checklist for that equipment and PM service into the ticket's maintenance record.
     c. Record the triggered service/threshold and update the equipment's current service state so
        repeating the action is idempotent.
     d. Append ticket history (`Ticket created — manual hour-meter service check`) and create
        in-app notifications for Super Admin, Manager, and Biman Admin.
  6. The service-check operation must be idempotent: repeated clicks/requests for the same
     equipment, service band, and maintenance cycle must not create duplicate tickets. Enforce
     this with a transaction plus a unique business key or an equivalent locked lookup.
  7. Because bands are contiguous and gap-free (§5.2), a single service-check may need to walk
     through more than one crossed band if the meter jumped by a large amount (e.g. skipped
     straight from below D-Service to above E-Service). Create one ticket per crossed band, in
     ascending order, unless the business decides only the highest crossed band should get a
     ticket — confirm this with stakeholders (see §9).
  8. A manual service-check may be performed immediately after recording the meter or later. It
     must use the latest persisted meter value and must be auditable (`triggeredByUserId`, time,
     previous value, current value, and selected service band).
  9. Do not put hour-meter crossing in a cron job, `SchedulerModule`, or BullMQ recurring job.
     BullMQ may be used for asynchronous in-app notification delivery after the transaction.

### 5.4 Maintenance Schedules (V-Service only)

- `MaintenanceSchedule` is only for recurring **V-Service**, every 6 months, with `lastDate`,
  `dueDate`, `status` (`Scheduled | Due soon | Overdue`), and optional linked `ticketId`.
- A scheduled job may recompute `status`:
  - `Due soon`: `dueDate` within `DUE_SOON_DAYS` (15 days, per `app/schedule/page.tsx`) of now.
  - `Overdue`: `dueDate` in the past.
  - `Scheduled`: otherwise.
- When a V-Service schedule becomes due (`dueDate <= now`) and has no open linked ticket:
  1. Create one `V-Service` PM ticket for the equipment.
  2. Link `MaintenanceSchedule.ticketId` to the new ticket.
  3. Create in-app notifications for the relevant operational users.
- When a V-Service ticket is closed/verified, create the next schedule row:
  `lastDate = closedDate`, `dueDate = lastDate + 6 months`, `status = Scheduled`, and no linked
  ticket for the new cycle.
- No F/B/C/D/E service is scheduled. Those services are triggered only through the explicit
  manual hour-meter service-check described in §5.3.

### 5.5 Tickets — Types, Priority, Status

- PM `serviceType` values are `F-Service | B-Service | C-Service | D-Service | E-Service |
  V-Service | Others`.
  - F/B/C/D/E are the standard hour-meter-band PM services. They are generated only by the
    explicit manual hour-meter service-check (§5.3), never by a scheduler and never from the
    ordinary manual ticket form.
  - `Others` is the PM ticket type for a **custom hour-band service** defined on an equipment type
    (§5.2) — any hour-band service beyond the standard F–E set. It is generated the exact same way
    as F/B/C/D/E: only via the manual hour-meter service-check when that custom band is crossed.
    `Ticket.pmServiceId` always identifies which specific `EquipmentTypeService` triggered an
    `Others` ticket, since an equipment type could in principle define more than one custom band.
  - V-Service is the only calendar-scheduled PM service (§5.4).
- User-created ticket types are **only** `Breakdown`, `General`, and `Washing`, and these can be
  created by Super Admin, Manager, and Biman Admin. `faultDescription`/problem description is
  required.
- `Others` must never be exposed as a manually selectable type in the create-ticket form/DTO — it
  is exclusively an auto-generated PM ticket type, on the same footing as F/B/C/D/E, not a
  user-created category.
- `TicketStatus` lifecycle (linear, matches the stepper in `app/tickets/[id]/page.tsx`):
  `Open → Assigned → In Progress ⇄ Awaiting Parts → Awaiting Verification → Completed → Closed`.
  - `Open`: created, unassigned.
  - `Assigned`: engineer assigned (assignment triggers a notification to that engineer).
  - `In Progress`: engineer has started work (`Start work` action, Engineer only, from
    `Open`/`Assigned`).
  - `Awaiting Parts`: set when a linked `EquipmentRequest` is pending (optional explicit
    transition or derived state).
  - `Awaiting Verification`: engineer submits the maintenance record/final feedback
    (`Final submit`) — checklist, parts used, labour hours, functional/safety checks, feedback
    required (non-empty).
  - `Completed`/`Closed`: Manager/Super Admin action (`Verify & close`) — reviews the maintenance
    record and closes the ticket, sets `closedDate`, `downtimeHours` (computed or entered).
  - Any transition/edit appends a `TICKET_HISTORY` row (actor + label + timestamp) and emits a
    notification (per requirements: "other actions on the ticket generate notifications").
- **Priority**: `Low | Medium | High | Critical` — settable at creation and editable by
  Manager/Super Admin.
- **Assignment**: Manager/Super Admin assign/reassign an engineer to a ticket at any time before
  closing → notification to the newly assigned engineer.
- **Editing**: Manager/Super Admin can edit priority, assigned engineer, due date, requesting
  party while the ticket is open (`editing` state in UI). Engineers cannot edit ticket metadata,
  only their maintenance-record/checklist/feedback fields.
- Only Manager/Super Admin can perform "Verify & close" (final authority), regardless of who
  created the ticket (including Biman-Admin-created tickets).

### 5.6 Inspection Checklist

- A master checklist template exists per (equipment type, or globally — current mock data uses
  one **shared 60-item checklist** across all equipment types, grouped into categories: `Body
  Work, Engine, Transmission, Rear Axle, Brake, Hydraulic, Wheels & Suspension, Electrical,
  Greasing, Safety, General`).
- Model as `CHECKLIST_TEMPLATE_ITEM(id, equipment_type_id NULLABLE, category, label, sort_order)`
  — `equipment_type_id NULL` = applies to all types (global default), otherwise type-specific
  overrides. This is inferred from the requirement *"Based on the service type inspection
  checklist is different"* — the current mock only ships one template, so the schema should
  support **per-service-type / per-equipment-type checklist templates** even though seed data may
  only populate one.
- When a ticket is created, clone the applicable template's items into
  `CHECKLIST_ITEM(maintenance_record_id, category, label, checked=false)`.
- Engineer toggles items via `PATCH /tickets/:id/checklist/:itemId`.

### 5.7 Parts / Equipment Requests

- Engineers (assigned to a ticket) can create requests: `item, quantity, reason` → status
  `Pending`.
- Biman Admin (and Super Admin/Manager) approve or reject a pending request → status
  `Approved`/`Rejected`, `approvedBy`, `approvedDate` set → notification to the requesting
  engineer (`Request Approved` / `Request Rejected`).
- Approved requests are later marked `Received` (by whoever fulfills, e.g. Biman Admin or
  Manager) → notification optional.
- A ticket may move to `Awaiting Parts` while a linked request is `Pending`/`Approved-not-yet-
  received`.
- Creating a request always emits a `New Request` notification to Biman Admin (and
  Manager/Super Admin).

### 5.8 Notifications

Persisted, per-user (or broadcast to a role) `AppNotification` rows. Trigger matrix:

| Event | Recipients |
|---|---|
| Ticket created (manual or auto) | Super Admin, Manager, Biman Admin |
| Engineer assigned to a ticket | The assigned engineer (+ optionally Manager/Super Admin) |
| Ticket status changed / edited / closed | Ticket creator, assigned engineer, Manager/Super Admin |
| Equipment hour meter crosses a service threshold | Super Admin, Manager, Biman Admin |
| V-Service schedule becomes due | Super Admin, Manager |
| Maintenance schedule overdue / due soon | Super Admin, Manager |
| Equipment/parts request created | Biman Admin, Manager, Super Admin |
| Equipment/parts request approved/rejected | Requesting engineer |
| New user created / password reset | The new user |

- Notifications have `read: boolean`; endpoints: list (paginated, filter by read/unread),
  mark-read, mark-all-read.
- Delivery: persist to Postgres + publish to Redis pub/sub channel (or WebSocket gateway backed by
  Redis adapter) for real-time in-app updates. BullMQ may provide retryable asynchronous delivery.
  Email delivery is explicitly out of scope for this version.

### 5.9 Equipment Documents

- Equipment documents (`Manual | Insurance | Certificate | Other`) may be uploaded and stored with
  metadata and an optional expiry date for display/reference. Files are stored on the local
  filesystem via the StorageModule (§5.11); PDFs are stored as-is (no transformation), subject to
  the document size limit.
- Document-expiry scanning, expiry notifications, and document-expiry jobs are out of scope for
  this version.

### 5.10 Reports

- Aggregate, read-mostly endpoints: equipment availability %, downtime/MTBF (mean time between
  failures) from ticket `downtimeHours` + `closedDate`, PM compliance (scheduled work completed
  on/before due date vs. late). Can be computed on-demand with SQL aggregates initially; consider
  materialized views or a nightly BullMQ job if datasets grow.

### 5.11 Local File Storage & Image Optimization

The app is image-heavy (equipment photos, engineer work images, feedback attachments). Store
files on the backend server's local filesystem, but **never store original camera photos** — every
image is re-encoded and resized before it is written to disk. Image optimisation reduces disk usage,
network transfer, backup size, and future migration cost.

#### Upload flow (backend-proxied)

Images go through the backend rather than being written by the frontend, because optimization
must happen *before* storage and the backend must control file validation, access permissions, and
filesystem paths.

1. Client sends `multipart/form-data` to a StorageModule endpoint, e.g.
   `POST /files/images` with `purpose` (`EQUIPMENT_PHOTO | WORK_IMAGE | FEEDBACK_IMAGE`) and the
   owning entity ID. Use `multer` **memory storage** with hard limits (see table below).
2. Authorize by purpose: equipment photos → Super Admin/Manager; work/feedback images → the
   engineer assigned to the ticket (and Super Admin/Manager).
3. Validate the real file type from its bytes (`sharp().metadata()`), not the client
   `Content-Type` or file extension. Reject anything that is not JPEG, PNG, WebP, or AVIF.
4. Optimize with **`sharp`**:
   - `.rotate()` first (apply EXIF orientation), then strip all metadata (EXIF/GPS) — smaller
     files and no location leakage.
   - Resize to fit within **1600 × 1600 px** (`fit: 'inside'`, `withoutEnlargement: true`).
   - Encode as **WebP, quality ~75–80** (`effort: 4`). WebP is chosen over AVIF for faster
     encoding and universal browser support; AVIF may be evaluated later.
   - Generate a **thumbnail variant**: 320 px, WebP quality ~70, used for lists, grids, and
     ticket/feedback previews.
   - Set `limitInputPixels` (e.g. 40 MP) to guard against decompression-bomb images.
5. Write both variants to a private application-managed directory (`Content-Type: image/webp`,
   `Cache-Control: private, max-age=31536000, immutable` at the HTTP layer — keys are content-unique,
   so files never change).
6. Insert a `FILE_ASSET` row and return `{ id, url, thumbnailUrl, width, height, sizeBytes }`.
7. If the file write succeeds but the DB insert fails (or vice versa), delete the local files in
   the error path; the orphan cleanup job (below) is the safety net.

Rough budget (approximate, depends on photo content): a 3–8 MB phone photo becomes
~150–350 KB at 1600 px WebP, plus ~15–30 KB for the thumbnail — roughly **25–50k images in
10 GB** instead of ~2k unoptimized originals, although actual capacity depends on the server disk
and backup-retention policy.

Image processing is CPU-bound. Run it synchronously in the request for single images, but cap
concurrency (e.g. `sharp.concurrency(1)` plus a small in-process semaphore) so bursts of uploads
don't starve the API. If upload volume grows, move processing to a BullMQ `image-processing`
worker.

**HEIC/HEIF (iPhone photos)**: the prebuilt `sharp` binaries do not decode HEIC. The frontend
should request JPEG from the camera/file picker or convert client-side before upload. Optionally,
the frontend may also downscale/compress before upload (e.g. `browser-image-compression`) to save
mobile bandwidth — the server still re-encodes regardless, as client output is untrusted.

#### Documents

- `POST /files/documents` — PDF (and optionally JPEG/PNG scans), stored as-is, no re-encoding.
- Validate by magic bytes; enforce the document size limit.
- Image scans uploaded as documents go through the same image pipeline, but with a 2400 px cap
  so text stays legible.

#### Limits (configurable via env)

| Setting | Default |
|---|---|
| Max image upload size (before optimization) | 15 MB |
| Max document upload size | 10 MB |
| Max images per feedback entry / work-image set | 10 |
| Max `OTHER` equipment photos per equipment | 10 |
| Stored image max dimension | 1600 px (2400 px for document scans) |
| Thumbnail dimension | 320 px |
| WebP quality (full / thumb) | 78 / 70 |

#### `FILE_ASSET` table

`id (uuid), relative_path, thumbnail_relative_path (nullable), purpose, mime_type, size_bytes,
thumbnail_size_bytes, original_size_bytes, width, height, sha256, status (PENDING | ATTACHED),
uploaded_by_user_id FK, created_at, attached_at, deleted_at`.

- `original_size_bytes` vs `size_bytes` lets Reports show how much space optimization saves.
- `sha256` of the optimized output may be used to dedupe identical uploads for the same entity.
- **Filesystem path layout** (no user-supplied filenames in paths):
  - `equipment/{equipmentId}/photos/{assetId}.webp` (+ `{assetId}_thumb.webp`)
  - `tickets/{ticketId}/work-images/{assetId}.webp`
  - `tickets/{ticketId}/feedback/{feedbackId}/{assetId}.webp`
  - `equipment/{equipmentId}/documents/{assetId}.pdf` (original filename kept only in DB)
- Store only a normalized relative path in the database; resolve it against `LOCAL_UPLOAD_ROOT`.
  Do not expose relative paths or filesystem paths directly to clients.

#### Upload-then-attach lifecycle

The ticket UI uploads images before the engineer presses "Final submit", so assets are created as
`PENDING` and become `ATTACHED` when the owning record (feedback entry, work images, equipment
photo slot) is saved. `PENDING` assets older than 24 h are deleted by the
`storage-orphan-cleanup` job.

#### Delivery (reads)

- Keep the upload directory outside the public web root. Serve files through authenticated
  controller endpoints, for example `GET /files/:id` and `GET /files/:id/thumbnail`, after checking
  the current user's permission to view the owning equipment/ticket.
- Set `Content-Type`, `Content-Length`, `ETag`, and a restrictive `Cache-Control` header. Use
  `Content-Disposition: inline` for images and `attachment` for documents where appropriate.
- Frontends should render thumbnails by default and load the full image only on click/zoom.
- If the app later runs behind a reverse proxy/CDN, configure private caching carefully; do not
  make the upload directory or raw filesystem paths publicly accessible.

#### Deletion & retention

- Deleting/replacing a photo, work image, feedback image, or document deletes its local files
  and soft-deletes the `FILE_ASSET` row.
- Soft-deleted equipment keeps its files until a hard purge is performed by Super Admin (files
  are referenced by historical tickets).

#### Quota monitoring

- Track usage in Postgres as `SUM(size_bytes + thumbnail_size_bytes)` of non-deleted assets.
  Periodically reconcile this against a filesystem scan to detect missing or orphaned files.
- The `storage-usage-check` job notifies Super Admin in-app when usage crosses **80%** and
  **95%** of `STORAGE_QUOTA_BYTES` (configurable; set it to the actual server-disk budget). Uploads
  may optionally be rejected with a clear error at 100%.
- Expose `GET /files/usage` (Super Admin) returning used bytes, quota, asset count, and bytes
  saved by optimization.

#### Configuration

`LOCAL_UPLOAD_ROOT`, `STORAGE_QUOTA_BYTES`, `STORAGE_PUBLIC_BASE_URL` (optional; prefer API
routes), plus the limits above. Use an absolute upload root outside the application source and
compiled output. In development, use a separate local directory such as `./var/uploads`; do not
store uploads in `public/` or commit them to Git.

## 7. Background Jobs (BullMQ + Redis)

Redis backs BullMQ queues and can double as a cache / pub-sub layer for realtime notification
delivery.

| Queue | Trigger | Job |
|---|---|---|
| `v-service-schedule-check` | Cron (daily) | Recompute V-Service schedule status and create a V-Service ticket when a due occurrence has no open ticket |
| `notification-dispatch` | Enqueued by notification-producing actions | Persist notification rows and push via WebSocket/Redis pub-sub; no email |
| `ticket-sla-check` (optional) | Cron (hourly/daily) | Flag overdue tickets (`dueDate` passed, not closed), notify Manager/Super Admin |
| `storage-orphan-cleanup` | Cron (daily) | Delete local files and rows for `PENDING` file assets older than 24 h (§5.11) |
| `storage-usage-check` | Cron (daily) | Compute local filesystem usage from `FILE_ASSET` plus reconciliation scan; notify Super Admin at 80% / 95% of quota |
| `image-processing` (optional, later) | Enqueued on upload | Move `sharp` optimization off the request path if upload volume grows |
| `reports-materialize` (optional) | Cron (nightly) | Precompute heavy report aggregates |

There is no recurring hour-meter service-check job. Hour-meter service crossing is initiated
manually by an authorized user through the service-check API/action. The API transaction may enqueue
only the resulting notification delivery job.

Use idempotent jobs where BullMQ is used (for example,
`notification-dispatch:ticket:${ticketId}`) and enforce service-check idempotency in the database
transaction with a unique business key or an equivalent locked lookup.

## 8. Tech Stack & Cross-Cutting Concerns

- **Framework**: NestJS (modular, DI, guards, interceptors, pipes).
- **Database**: PostgreSQL via TypeORM or Prisma (pick one; Prisma recommended for schema clarity
  and migrations — adjust module scaffolding accordingly). Use the domain requirements in this
  document and the approximate PlantUML diagram as inputs; the final schema may be improved during
  implementation.
- **Cache/Queues**: Redis + BullMQ (`@nestjs/bullmq`).
- **Auth**: JWT (access + refresh), `passport-jwt`, `bcrypt`/`argon2` for password hashing,
  `@nestjs/throttler` for rate limiting login attempts.
- **Validation**: `class-validator` / `class-transformer` DTOs on every endpoint.
- **API docs**: `@nestjs/swagger`, tag controllers by module, document all DTOs and enums,
  generate `swagger.json` for the frontend team.
- **File storage**: Local filesystem managed by `StorageModule`; uploads proxied through the
  backend with `multer` (memory storage) and optimized with `sharp` before storage; metadata in
  `FILE_ASSET` (see §5.11).
- **Pagination/filtering**: standard `?page&limit&sort&search` query params on all list endpoints
  (equipment, tickets, requests, notifications, users).
- **Audit trail**: generic interceptor or explicit history tables (`TicketHistory`,
  `HourMeterReading`) — avoid over-engineering a generic audit log unless required later.
- **Testing**: unit tests for business rules (especially §5.3 threshold-crossing logic and §5.4
  recurrence logic — these are the trickiest and most valuable to cover), e2e tests per module
  with a test Postgres/Redis via Docker Compose.
- **Environment**: Docker Compose for local Postgres + Redis; `.env` for secrets (never commit).

## 9. Open Questions / Assumptions (flag to stakeholders before finalizing schema)

1. **Checklist templates**: mock data has one shared 60-item checklist, but the requirement states
   that the checklist differs by service type. Confirm whether templates should be authored per
   `EquipmentType`, per PM service (`F/B/C/D/E/V/Others`), or both. Recommendation: key templates
   by `(equipment_type_id, pm_service_id)` with fallback to a global default, since `Others` can
   represent a different custom service per equipment type.
2. **Hour-meter decrease handling**: assume hour meters are monotonic; decide whether corrections
   need a separate audited correction workflow.
3. **PM ticket due date**: the mock does not define a grace period after a manual hour-meter
   service-check. Choose a configurable default or require the operator to enter a due date.
4. **Downtime hours**: currently manually entered per ticket in the mock. Decide if this should be
   auto-computed from `createdDate`/`closedDate` timestamps instead/also.
5. **Biman Admin's own users**: currently view-only "Biman users" list is seeded, not managed via
   the app — confirm whether Biman-side user provisioning happens elsewhere or should also be
   Super-Admin-managed.
6. **Image delivery**: confirm that authenticated API routes are sufficient, or decide whether a
   reverse proxy/CDN should be added later for private caching. Do not expose the upload directory
   directly.
7. **Image quality**: confirm 1600 px / WebP q78 is sufficient for inspection evidence (e.g.
   reading serial plates or damage close-ups). Raise to 2048 px if engineers need more detail;
   storage per image grows roughly with pixel count.
8. **Multiple bands crossed at once**: if the hour meter jumps far enough to cross more than one
   band since the last service-check (e.g. skipping straight past D-Service into E-Service),
   confirm whether the backend should create a ticket for every crossed band or only the highest
   one. §5.3 defaults to "one ticket per crossed band" pending confirmation.
9. **Multiple custom (`Others`) bands per equipment type**: confirm whether an equipment type may
   define more than one custom hour-band service (all sharing ticket type `Others`, disambiguated
   by `pmServiceId`), or whether the business only ever needs at most one custom band per type.
